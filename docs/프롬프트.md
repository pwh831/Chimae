# 바이브코딩 단계별 프롬프트

회상 게임 데모 제작용. 각 단계는 **독립적으로 실행·확인 가능**하도록 나누었다.

---

## 시작 전 원칙

바이브코딩이 무너지는 가장 흔한 원인은 한 번에 너무 많이 시키는 것이다. 아래 네 가지만 지키면 대부분 막힌다.

1. **한 프롬프트 = 한 화면 또는 한 기능.** 여러 개를 묶어 요청하지 않는다
2. **각 단계가 끝나면 반드시 직접 실행해 눈으로 확인한다.** 확인 없이 다음 단계로 넘어가면 어디서 깨졌는지 못 찾는다
3. **AI는 mock 데이터로 나중에 붙인다.** 처음부터 API를 연결하면 UI 문제인지 AI 문제인지 구분이 안 된다
4. **작동하는 시점마다 저장(커밋)한다.** 되돌아갈 지점이 없으면 한 번 꼬였을 때 처음부터 다시 해야 한다

또 하나. AI가 "이것도 같이 개선했습니다"라며 손대지 않은 파일을 고쳐놓는 경우가 많다. **매 프롬프트 끝에 "요청한 파일 외에는 수정하지 마세요"를 붙이는 습관**을 들이면 사고가 크게 준다.

---

## 0단계 — 프로젝트 셋업과 디자인 기준

> React + Vite로 태블릿 가로 화면(1280x800 기준) 웹앱 프로젝트를 만들어줘.
>
> 이 앱은 초기·중기 치매를 겪는 어르신이 **혼자 손가락으로 조작**하는 앱이야. 다음 디자인 기준을 전역 CSS와 공통 컴포넌트로 먼저 잡아줘.
>
> - 기본 글자 크기 24px 이상, 버튼 안 글자는 32px 이상
> - 터치 영역 최소 100x100px, 버튼 사이 간격 넉넉하게
> - 배경과 글자 명도 대비를 크게 (흰 배경에 진한 회색 글자)
> - 화면당 선택지는 최대 4개
> - 애니메이션은 느리고 부드럽게, 깜빡임이나 빠른 움직임 금지
> - 색으로만 정보를 전달하지 않기 (아이콘·글자 병행)
>
> 공통 컴포넌트로 `BigButton`, `ScreenLayout`(제목 + 내용 + 하단 버튼 구조)을 만들고, 이 컴포넌트만 보여주는 확인용 페이지를 하나 띄워줘.
>
> 요청한 것 외의 기능은 만들지 마세요.

**확인**: 브라우저에서 버튼이 크게 보이고, 태블릿 크기에서 답답하지 않은지.

---

## 1단계 — 데이터 구조 고정

> 이 앱의 데이터 구조를 TypeScript 타입으로 정의하고, 샘플 데이터 파일을 만들어줘. 아직 화면은 만들지 마.
>
> 필요한 타입:
> - `Elder` — 어르신 정보 (이름, 호칭, 프로필 사진)
> - `LifeStory` — 가족이 입력한 생애 소재 (카테고리: 음식/장소/노래/물건/사람, 제목, 설명, 민감 주제 여부 플래그, 사진 URL)
> - `FamilyQuestion` — 손자녀가 낸 문제 (보낸 사람, 문제 내용, 선택지 3개, 함께 보낸 메시지, 사진, 보낸 날짜, 읽음 여부)
> - `Activity` — 회상 활동 (종류, 어떤 LifeStory에서 나왔는지, 활동 데이터)
> - `SessionLog` — 하루 활동 기록 (날짜, 참여한 활동, 어르신이 말한 내용, 반응이 좋았던 소재)
>
> 샘플 데이터는 가상의 인물 한 명(예: 82세 김순자님) 기준으로 생애 소재 5개, 손자 문제 2개를 채워줘. 김치찌개 레시피, 살던 동네, 좋아하던 노래가 포함되면 좋겠어.
>
> 타입과 샘플 데이터 파일만 만들고 다른 건 건드리지 마세요.

**확인**: 나중에 AI가 만들어낼 데이터도 이 구조에 들어맞는지 미리 상상해볼 것. 여기서 구조가 흔들리면 뒤에서 전부 고쳐야 한다.

---

## 2단계 — 홈 화면

> 어르신용 홈 화면을 만들어줘. 앱을 켜면 처음 보이는 화면이야.
>
> - 상단에 큰 글씨로 인사 ("순자님, 안녕하세요")와 오늘 날짜
> - 가운데에 아주 큰 카드 하나: 손자녀가 보낸 새 문제가 있으면 "손녀 지민이가 문제를 보냈어요" + 프로필 사진, 없으면 "오늘의 이야기를 시작해요"
> - 카드를 누르면 다음 화면으로 넘어가는 구조 (아직 다음 화면은 없으니 콘솔 로그만)
> - 하단에 작게 "지난 이야기 보기" 버튼 하나
>
> 화면에 다른 요소를 추가하지 마. 선택지가 많으면 어르신이 혼란스러워해. 1단계 샘플 데이터를 사용하고, 다른 파일은 수정하지 마세요.

**확인**: 화면에 누를 수 있는 게 두 개뿐인지. 세 개 이상이면 줄일 것.

---

## 3단계 — 손자녀 문제 풀기

> 손자녀가 낸 문제를 푸는 화면을 만들어줘.
>
> - 문제 텍스트를 큰 글씨로 표시
> - 선택지 3개를 세로로 크게 배치
> - **정답/오답 판정을 하지 않는 게 가장 중요해.** 어떤 선택지를 골라도 화면이 부드럽게 다음으로 넘어가야 해
> - 정답이 아닌 걸 골랐을 때: "그럴 수도 있겠네요" 같은 따뜻한 반응을 잠깐 보여주고 넘어가기
> - 정답을 골랐을 때: "맞아요!" 같은 반응
> - X 표시, 빨간색, 오답 표시, 점수는 절대 사용하지 마
> - 넘어간 뒤에는 메시지 화면 자리를 비워두고 "메시지 화면 예정"이라고만 표시
>
> 이 화면 파일만 만들고 다른 파일은 수정하지 마세요.

**확인**: 일부러 틀린 답을 눌러보고, 기분이 상하지 않는지 스스로 체감해볼 것. 이 감각이 서비스의 핵심이다.

---

## 4단계 — 메시지 확인과 답장

> 문제를 푼 뒤 손자녀 메시지를 보는 화면을 만들어줘.
>
> - 손자녀 사진과 메시지를 크게 표시
> - 함께 보낸 사진이 있으면 화면 대부분을 차지하게 크게
> - 아래에 답장 방법 두 가지: ① 큰 마이크 버튼 (누르고 있는 동안 녹음) ② 미리 준비된 문구 4개 중 선택 ("고마워", "보고 싶다", "잘 지내니", "사랑한다")
> - 녹음 기능은 아직 실제로 만들지 말고, 버튼을 누르면 "녹음 중..." 표시만 나오게 해줘
> - 답장을 보내면 "지민이에게 전했어요" 확인 화면
>
> 타이핑 입력은 넣지 마. 이 화면 파일만 만들어주세요.

---

## 5단계 — 회상 활동 (핵심)

> 레시피 순서 맞히기 회상 활동 화면을 만들어줘. 이게 이 앱의 핵심 기능이야.
>
> - 샘플 데이터의 김치찌개 소재를 사용
> - "순자님이 잘 만드시던 김치찌개예요. 순서를 맞춰볼까요?" 안내
> - 조리 단계 4개를 카드로 보여주고, 순서대로 탭해서 배열하는 방식 (드래그는 어르신에게 어려우니 탭으로)
> - 순서가 달라도 틀렸다고 하지 않고 "이렇게 만드는 분도 계시죠" 같은 반응
> - 마지막에 "김치찌개에 얽힌 이야기가 있으신가요?" 하고 자유롭게 말할 수 있는 화면 (마이크 버튼, 녹음은 아직 표시만)
> - 어르신이 말한 내용은 SessionLog에 저장되는 구조로
>
> 드래그앤드롭은 사용하지 마. 이 화면 파일만 만들어주세요.

**확인**: 여기까지가 결선 데모의 뼈대다. 3~5분 안에 도는지 실제로 재보기.

---

## 6단계 — 세션 마무리

> 오늘 활동을 마치는 화면을 만들어줘.
>
> - "오늘도 좋은 이야기 들려주셔서 고마워요" 인사
> - 오늘 한 활동을 간단한 그림 카드로 요약 (문제 풀기, 김치찌개 이야기)
> - "내일 또 이야기해요" 문구로 마무리 — 계속 하도록 유도하는 문구는 넣지 마
> - "가족에게 오늘 이야기를 전했어요" 안내
>
> 다시 시작하기 버튼이나 더 하기 유도는 넣지 마세요. 이 화면 파일만 만들어주세요.

---

## 7단계 — 전체 흐름 연결

> 지금까지 만든 화면들을 하나의 흐름으로 연결해줘.
>
> 홈 → 문제 풀기 → 메시지 확인 → 답장 → 회상 활동 → 마무리 → 홈
>
> - 상태 관리는 간단하게 (별도 라이브러리 없이 useState나 Context로 충분)
> - 각 화면 전환은 느리고 부드럽게
> - 뒤로 가기는 넣지 마 — 어르신이 길을 잃는다
>
> 새 기능은 추가하지 말고 연결만 해주세요.

**확인**: 처음부터 끝까지 한 번에 돌려보고 막히는 지점 찾기. **여기가 최소 시연 가능한 완성 시점이다. 반드시 저장해둘 것.**

---

## 8단계 — 가족용 소재 입력 화면

> 가족(손자녀)이 쓰는 화면을 만들어줘. 어르신용과 완전히 분리된 화면이고, 일반적인 모바일 앱 디자인이면 돼.
>
> - 생애 소재 입력 폼: 카테고리 선택, 제목, 짧은 설명, 사진 업로드, "민감한 주제일 수 있음" 체크박스
> - 입력 부담을 줄이는 게 핵심이야. 한 번에 하나씩 묻는 형태로, 한 소재당 30초 안에 끝나게
> - 등록된 소재 목록
> - 어르신의 오늘 활동 요약 보기 (반응이 좋았던 소재 표시)
>
> 어르신용 화면 파일은 건드리지 마세요.

---

## 9단계 — AI 연동

> 이제 AI를 붙일 거야. 가족이 입력한 짧은 소재를 회상 활동으로 바꾸는 기능이야.
>
> - Anthropic API를 호출해서, `LifeStory` 하나를 받아 레시피 순서 맞히기용 조리 단계 4개를 생성
> - 응답은 JSON만 반환하도록 프롬프트에 명시하고, 파싱 실패에 대비한 처리 포함
> - **API 호출이 실패하면 기존 샘플 데이터로 대체**해서 앱이 멈추지 않게 해줘 (시연 중 네트워크 문제 대비)
> - 생성 중에는 어르신 화면에 로딩을 보여주지 말 것 — 미리 만들어두는 구조로
>
> 한 가지 활동 종류만 먼저 해줘. 다른 활동은 나중에.

**확인**: 인터넷을 끊고 실행해서 앱이 계속 도는지 확인. 결선 현장에서 이게 생명줄이 된다.

---

## 10단계 — 음성 기능

> 마이크 버튼이 실제로 작동하게 해줘.
>
> - 브라우저 Web Speech API로 음성 인식
> - 인식 결과를 SessionLog에 저장
> - 인식이 안 되거나 권한이 없으면 조용히 넘어가고, 오류 메시지로 어르신을 놀라게 하지 말 것
> - 화면 안내 문구를 음성으로 읽어주는 기능도 추가 (읽어주기 켜기/끄기)
>
> 음성 관련 코드만 수정해주세요.

---

## 11단계 — 시연 준비

> 결선 시연용으로 다듬어줘.
>
> - 데모 시작 상태로 되돌리는 리셋 버튼 (개발자용, 구석에 작게)
> - 시연 시나리오대로 데이터 채우기: 손녀가 보낸 문제 1개 + 메시지 + 사진, 생애 소재 5개
> - 전체 흐름이 3~5분에 끝나는지 확인하고, 너무 길면 어디를 줄일지 알려줘
> - 오프라인에서도 완전히 작동하는지 점검
>
> 새 기능은 추가하지 마세요.

## 막혔을 때

- **AI가 엉뚱한 파일을 고쳤다** → 저장 지점으로 되돌리고, 프롬프트에 수정 금지 파일을 명시해서 다시 요청
- **화면이 깨졌는데 원인을 모르겠다** → 직전 단계로 되돌아가 한 번에 하나씩 다시 붙이기
- **요구사항이 자꾸 늘어난다** → PRD 10.1의 "핵심 플레이 1개"를 다시 읽기. 범위를 좁게 잡는 것 자체가 심사 항목이다
